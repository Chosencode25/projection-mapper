# v1.11.3 — Reusable looks, palettes and show controls

Planned and implemented October 6, 2026. This document records the implementation contract for the third slice of [v1.11](V1.11_PLAN.md). See [verification and delivery](V1.11.3_VERIFICATION.md): all 184 Debug/Release correctness tests passed; installed app is now v1.11/build 8. User visual acceptance remains pending. The steps below retain the original implementation order.

## Intended result

Save a named arrangement of content and appearance, recall it without moving mapped faces, reuse named colors across objects, and dim/fade/black out all rendered content from accessible controls. Editor preview and Test Window use the same state and renderer. Libraries belong to the project package.

Basic look recall is immediate. Music, cue timelines, animated transitions between looks, global libraries, library import/export, image/video imports and physical projector output remain in their existing later milestones. Routine visual checks remain the user's responsibility.

## Step 1 — Establish models and persistence contracts

Add project-owned looks, palettes and master settings using Codable, Equatable values and stable UUIDs. Keep each operation a validated session transaction suitable for later undo/redo. Do not persist transient render state.

| Value | Saved in project | Default |
| --- | --- | --- |
| Looks and palettes | Yes | Empty libraries |
| Owner color bindings and literal fallback colors | Yes | Existing literal colors; no bindings |
| Master brightness | Yes | 1; bounded 0–1 (0–100%) |
| Fade duration | Yes | 1 second; bounded 0–30 seconds |
| Fade gain/progress and blackout latch | No | Gain 1; blackout off |

Use schema 5; migrate schemas 1–4 with these defaults while preserving all existing IDs, layout, content, appearance and locks. Validate finite values, unique IDs, names and collection sizes before replacing session state. Initial limits: 100 looks, 100 palettes, 32 slots per palette, 80-character names, and 2,000 target entries per look, consistent with the existing face/object limits. Retain the existing manifest-size cap.

A saved look may contain targets that no longer exist; that is a supported stale-target condition with diagnostics. Active palette references must resolve to a palette and slot in the package; malformed or dangling references fail validation without replacing the open project. Normal deletion operations remove such references by materializing colors first. Literal fallbacks support stale in-memory resolution defensively, not silent acceptance of corrupt packages.

**Checkpoint:** round trips, old-format migration, invalid/newer documents and atomic-save failure tests pass before UI integration.

## Step 2 — Add palettes and explicit color ownership

A palette has a stable ID, editable name and ordered slots. Each slot has its own stable ID, editable name and bounded RGBA color. Renaming/reordering never changes references. Add create, rename, edit, add/remove slot and delete palette actions.

Bind either primary or secondary content color to a slot. Bindings live on the content owner: a standalone face or an object. A member face edits its shared object's colors; appearance overrides do not create independent content. Show the current scope and palette/slot name beside the color control. A direct literal color edit removes only that color's binding. Unlinking keeps the currently resolved color.

Resolve colors before producing the shared render snapshot. Editing a slot updates every owner bound to that slot and no unbound owners. Grouping/attaching use the adopted owner's bindings; detach and duplication preserve bindings to the same palette while creating the existing independent source identities. Generator/content reset clears bindings for colors it resets. Existing generator presets remain literal snapshots: saving captures resolved colors and applying clears the affected bindings.

Deletion uses one explicit policy: materialize current slot colors into every referencing live source and saved look, then remove references and the slot/palette in one transaction. Show the affected reference count in the deletion dialog; cancellation changes nothing. No automatic reassignment to another palette.

**Checkpoint:** shared-owner propagation, primary/secondary independence, copy/detach/reset/preset behavior and reference-safe deletion pass. Saving/reopening preserves the same resolved colors.

## Step 3 — Capture and apply named looks

The first version captures all current targets; partial-target authoring is deferred. Provide Save New Look, Rename, Update from Current, Apply and Delete. Updating replaces the stored payload while preserving the look ID. Overwrite/delete dialogs describe the affected look.

Capture each object once for shared content and object appearance. Capture standalone faces for their content and appearance. Capture member faces for their explicit appearance override, including the instruction to return to inheritance when the captured override is absent. Target keys include kind and UUID. Member-face entries also record their expected object ID as compatibility metadata.

Supported payload: content type, generator settings/seed, literal colors or palette bindings with captured fallback colors, and appearance including opacity, brightness, crop and flips. Literal look colors remain snapshots; palette-bound look colors follow the current slot value when recalled.

Exclude corners, input maps, object membership/mode, links, visibility, names/tags/order, geometry locks, masks, selection, playback phase/speed/pause, master brightness and runtime fades/blackout. Existing source IDs remain stable when content values change. A look cannot unlock, move, regroup or reveal a hidden face.

Resolve and validate the complete application before one project mutation. Apply compatible existing targets; leave newly added targets untouched. Missing targets and member faces whose object association changed are skipped and listed in the result. Never match names, recreate deleted targets or redirect an object entry to a face. An existing object entry affects its current members through normal shared ownership. Report applied/skipped counts, including a no-applicable-target result. Malformed payloads abort without partial application.

**Checkpoint:** snapshot/update/apply/delete tests, changed membership, deleted/duplicated targets, inherited overrides and unchanged layout/locks/playback pass. Look operations participate in dirty state and autosave; selecting a look does not.

## Step 4 — Implement master brightness, fades and blackout

Define the output calculation explicitly. Existing face brightness evaluates and clips each face's RGB, and existing opacity controls compositing. Multiply the composed content by master brightness × runtime fade gain. Immediate blackout forces RGB to zero. Master attenuation does not alter alpha or saved source colors; it must not reveal lower faces by reducing opacity. With the current black background, applying the same attenuation to each already-clipped fragment is equivalent to attenuating the final composition; GPU tests must establish this equivalence for overlap cases.

Fade gain is linear from its current evaluated value to 0 or 1 over the configured duration. Use monotonic elapsed time independently of generator transport. Pausing, seeking or changing generator speed does not change the fade clock.

- Fade to Black targets gain 0; Restore targets gain 1, relative to the current saved master brightness.
- Reversing a fade starts from its current gain with no discontinuity and uses the configured duration for the new transition. Repeating the current target is a no-op.
- Zero duration applies the target immediately. Changing duration affects the next action. Changing master brightness during a fade takes effect immediately without resetting fade progress.
- Blackout acts immediately, latches on, cancels an active fade and holds runtime gain at 0. Repeated Blackout or Fade to Black while latched leaves it black.
- Restore clears the latch and fades from the currently black output toward gain 1. A look or brightness edit cannot clear blackout. A saved master brightness of zero therefore stays black even after Restore.
- New/Open/recovery reset fade gain to 1 and blackout off, using the loaded master setting. Saving does not reset runtime state. Output close/reopen preserves session state and evaluates the current elapsed time.

Blackout/fades do not pause or restart generators and will not silently control future audio. Their actions and progress never dirty the project, create recovery writes or enter future undo history.

**Checkpoint:** deterministic injected-time tests cover completion, reversal, repeated actions, interruption, zero duration, transport independence, opening projects and output-window lifecycle.

## Step 5 — Integrate rendering and accessible controls

Carry one session-owned master/fade snapshot into editor and Test Window scenes. Both evaluate the same monotonic clock and transition anchor; neither view owns a separate fade timer. Add rendering demand for an active fade even when all content is static or paused, and issue the final frame when it completes. Hidden/closed views do not drive unnecessary rendering; elapsed time still advances. Settled black output can idle while preserving logical generator phase for restoration.

Add project-level Looks, Palettes and Master Output sections in the inspector, with reusable color binding controls in the existing source inspector. Master Output offers brightness, duration, Fade to Black and Restore, plus a clear status such as Normal, Fading or Blackout. Keep Blackout and Restore reachable from the toolbar/menu even when the inspector is hidden. Editor selection outlines and controls remain available during blackout; clean output remains undecorated.

Proposed menu shortcuts: Command-Shift-B for immediate Blackout and Command-Shift-R for Restore. Check native routing and conflicts during implementation; retain normal typing and corner/object nudging. Do not use an unmodified letter or Space as the blackout shortcut.

**Checkpoint:** shared snapshot/state actions pass automated checks; renderer demand settles after completion, and reopened output has the correct gain without a flash.
