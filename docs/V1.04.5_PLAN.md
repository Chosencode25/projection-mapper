# v1.04.5 — Performance and Acceptance

Status: all seven steps implemented and locally accepted October 5, 2026 for Test Mode. See [verification and measurements](V1.04.5_VERIFICATION.md) and [master plan](V1.04_PLAN.md). The following steps retain the agreed requirements.

## Outcome and measurement rules

Finish v1.04 with a measured, stable shared renderer for the diagnostic rectangle. Preserve on-demand drawing and normalized geometry. Report actual performance on the development Mac, with enough information to repeat the measurements.

The renderer currently draws only when invalidated. Idle FPS is therefore not a useful success criterion. Measure redraw count, CPU encoding cost, GPU execution cost, and request-to-completion latency separately. GPU completion is not proof of visible presentation latency.

Preset selection controls aspect ratio and simulated output metadata; native drawable pixels follow the fitted view and backing scale. A 4K label does not establish 4K rendering. Measure native view workloads and exact-resolution offscreen textures separately. Forced benchmark submissions must not introduce a continuous loop into the production app.

## Step 2 — Add measurement support

- Add a small optional diagnostic sink around renderer submission and completion. Record view identity, submission count, skipped reason, actual pixel dimensions, CPU encode duration, submission/completion timestamps, and GPU start/end timestamps when supported.
- Keep diagnostics off by default and avoid a new product-facing panel. Use bounded samples, weak ownership where appropriate, and no retained command buffers or drawables after completion.
- Handle missing GPU timestamps as unavailable, rather than zero. Distinguish encode duration from queue delay, GPU execution, and full completion latency.
- Add a benchmark helper that calls the existing encodeScene implementation with controlled offscreen textures. Keep waits/readback out of CPU encode timing; GPU timing comes from completed command buffers.
- Keep production command submission asynchronous. The benchmark may wait for completion outside normal rendering.
- Test sample accounting, disabled diagnostics, unavailable timestamps, and cleanup if new diagnostic code creates ownership relationships.

Completion: reliable measurements with no rendering behavior change when diagnostics are disabled.

## Step 3 — Measure the workload matrix

Exact-resolution offscreen matrix:

| Preset | Texture pixels |
|---|---|
| HD | 1280 × 720 |
| Full HD | 1920 × 1080 |
| 4:3 | 1024 × 768 |
| Portrait | 1080 × 1920 |
| 4K | 3840 × 2160 |

- Use Release builds and the same geometry, color, shaders, and pixel format as production.
- Warm up 30 submissions per texture size. Collect 300 measured submissions per size, repeat three times, and record median, p95, and maximum CPU encode/GPU execution times. If timestamps are unavailable, label the substitute measurement precisely.
- Run sequential submissions to isolate per-frame cost. Separately run a bounded two-view workload to represent editor plus output; measure aggregate cost without deriving it by simply doubling one result.
- Validate representative rectangle/background pixels outside timed samples.
- For native views, use wide 800 × 450, tall 400 × 600, and square 600 × 600 point windows across all five presets. Log fitted view points, backing scale, and actual drawable pixels for each. Repeat with editor and output together where window presentation is available.
- If a native test window is reported occluded, record that state. Its drawable allocation is not evidence of a visibly presented frame.
- Inspect idle CPU and memory separately from isolated GPU benchmarks. Use available command-line profiling tools; if GPU utilization profiling is unavailable, report execution timing and do not substitute a utilization claim.

Completion: saved raw samples under builds/v1.04.5/ and a readable table distinguishing native drawable measurements from exact-size GPU workloads.

## Step 4 — Check idle behavior and lifecycle performance

- After a two-second settling period, sample each static state for ten seconds: editor only, editor plus output, output minimized, hidden/occluded views, and output closed.
- Check submitted-frame counters stay unchanged while static and settled, with no submissions from suspended views. Explain any OS-triggered invalidation rather than ignoring it.
- Exercise 50 output open/close cycles and 100 preset changes. Check weak-reference deallocation, surviving renderer/view counts, GPU completion errors, and process memory before/after warmup and the repeated operations.
- Require released output view/renderer counts to return to baseline after autorelease pools drain. Memory may retain allocator caches; investigate growth over three repeated batches rather than claiming a leak from one high-water mark.
- Measure redraw request-to-GPU-completion after a view becomes eligible, resize settles, and a preset changes. Report p95 and maximum; identify whether results came from genuine window events or a synthetic harness.
- Evaluate a provisional 16.7 ms GPU budget for one rectangle frame at actual 4K, plus a measured budget for both views. This is a comparison target, not an advance promise of 60 FPS or measured display pacing. Establish the final supported target from results.

Completion: no unexplained sustained idle submissions, no ownership accumulation, no GPU errors, and documented latency/resource results.

## Step 5 — Make only justified fixes

- Investigate measured issues such as redundant invalidations, drawable acquisition delays, unnecessary allocations, or resource retention.
- Preserve shared scene behavior and separate view ownership. Avoid speculative pipeline caching or architectural rewrites unless measurements show a benefit.
- Add a focused regression for each actual behavioral fix. Rerun affected measurements with identical conditions and record before/after results.
- If no bottleneck is found, keep the renderer as it is and document that outcome. If a target is missed, fix the cause or report the achievable limit explicitly.

Completion: evidence-backed improvements, or a documented baseline requiring no tuning.
