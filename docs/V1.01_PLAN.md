# Projection Mapping App — v1.01 Plan

## 1. Purpose

v1.01 builds the foundation of the native Mac app: a working control window with a toolbar, surface sidebar, empty editor canvas, basic project state, and a structure for adding projection features.

This is the first development milestone in the 15-stage V1 roadmap. The complete first usable mapper arrives at v1.15.

The eventual workflow is to choose a test output or projector, add media or an animation, create a surface, drag its corners into alignment, view clean output, and save the project.

## 2. Development approach

Build with **Xcode 27.0 beta 5 (27A5237l)** using Swift. Read PROJECT_DEVELOPMENT.md before implementation.

- SwiftUI for interface layout, panels, toolbar, and state presentation.
- Programmatic AppKit for Mac window behavior where needed.
- Metal for rendering beginning in v1.04.
- AVFoundation for video beginning in v1.09.

Write all interface design in code. No storyboards, XIBs, or required visual interface construction. Use built-in Apple frameworks; v1.01 needs no third-party dependencies.

Record the chosen minimum macOS deployment target before implementation. Build and verify using the required Xcode release before claiming compatibility.

## 3. Included features

- Runnable macOS application with one main control window.
- Toolbar, empty surface sidebar, empty central canvas, project inspector, and status area.
- In-memory project model, New Project command, and editable project name.
- About window showing version 1.01.
- Standard Mac window controls and working resizing.
- Documented source organization for later stages.

The app must launch and operate without a projector. Rendering, media, surfaces, output windows, and saving belong to later milestones.

## 4. Main control window

Use a three-column editor: surface sidebar on the left, canvas in the center, and project inspector on the right, with a toolbar above and status area below.

Starting dimensions:

- Window: approximately 1200 × 800 points.
- Minimum: approximately 900 × 600 points.
- Sidebar: approximately 220 points wide.
- Inspector: approximately 260 points wide.
- Canvas: remaining space.

Adjust these choices based on testing. Use a dark editor appearance, readable text, clear panel boundaries, and familiar Mac controls.

## 5. Toolbar

Include New Project, the current project title, a sidebar visibility toggle, and an inspector visibility toggle. Reflect the project name in the window title.

Only implemented actions should be active. Add Save, import, playback, calibration, and output controls when their features exist.

## 6. Surface sidebar

Label it “Surfaces.” Its initial empty state reads “No surfaces yet,” with “Your mapped surfaces will appear here.”

Do not populate fake surfaces. Surface creation begins in v1.05. Structure the view so a real list can replace the empty state later.

## 7. Empty editor canvas

Show a dark workspace with a centered, bounded 16:9 preview area. Keep it centered and preserve its aspect ratio during resizing. Label it “Mapping Preview” with a brief empty-state explanation.

Keep all content inside its boundary. Its displayed size is not a projector resolution. This stage has no render loop, draggable nodes, media, or projected output. Separate decorative styling from future calibration patterns.

## 8. Project inspector

Label it “Project.” Include an editable Name, a read-only Surface count of zero, and Output status “Not configured.”

Default name: “Untitled Project.” Update toolbar and window title immediately when the name changes. Trim surrounding whitespace when editing finishes; restore the default if the name is empty.

Surface-specific settings will extend or replace this panel when surface selection exists.

## 9. Project model and session state

Keep data separate from views. MappingProject contains a stable project ID, name, creation date, and modification date.

EditorSession tracks the active project, panel visibility, and whether project data has user changes. Panel visibility is interface state, not projection data.

Surface count is zero. Define the actual surface model in v1.05. Project data is in memory only; persistence starts in v1.14.

## 10. New Project behavior

Launch with one empty “Untitled Project.”

New Project checks whether user changes exist. An unchanged project resets immediately. A changed project presents Discard and Cancel. Discard creates a new ID and timestamps and restores the empty project; Cancel preserves the current state.

Explain in the discard message that this milestone cannot save. Apply the same protection when closing or quitting with user changes. Share the behavior through one lifecycle coordinator.

## 11. Window and application behavior

Support one active project in one editor window. Standard close, minimize, maximize, and resize controls work. Closing an unchanged window needs no confirmation. Activating the app after closing its editor can reopen the editor. Quitting ends the app cleanly.

Keyboard focus works in the name field, and menus and toolbar remain usable with hidden panels. Use explicit lifecycle coordination where default SwiftUI behavior is insufficient.

The model owns project data, the session owns current editor state, views display it and invoke actions, and the lifecycle coordinator manages window creation and discard protection. Do not create empty future subsystems just to reserve names.

## 14. Preparation for Test Mode

v1.02 adds Test Window or connected-display selection. v1.03 adds the separate resizable test output and fullscreen projector output. v1.04 adds their shared renderer.

For v1.01, keep editor layout independent of output sizing. Later test-window resizing must affect only display size, not mapping or simulated resolution. The output window is not part of v1.01.

## 15. Implementation sequence

1. Create the native macOS SwiftUI project in app/, set identity and version 1.01, and verify an empty launch.
2. Implement model and session state: defaults, naming, timestamps, and change tracking.
3. Build separate toolbar, sidebar, canvas, inspector, and status views, with resizing and visibility controls.
4. Connect naming, New Project, and discard protection.
5. Implement menus, shortcuts, About, editor reopening, and consistent close/quit behavior.
6. Run acceptance checks, fix problems, and produce a local development build.

## 16. Verification

Manually verify launch without a display; minimum and large window sizes; panel hiding and restoration; name updates; empty-name handling; new project with and without changes; cancel and discard on reset, close, and quit; reopening; keyboard navigation; centered aspect-preserving canvas; and truthful active controls.

Add focused automated tests for independent reset and change-tracking logic if implemented. Extensive interface tests are unnecessary for this milestone.

## 17. Completion criteria

1. The app builds and launches using Xcode 27.0 beta 5 (27A5237l).
2. The control-window layout works and active controls perform their stated actions.
3. Project naming, reset, and discard protection behave consistently.
4. Resizing produces no clipped or overlapping controls.
5. The app runs without a projector.
6. The interface is entirely code-based.
7. The source is ready for v1.02 output selection.
8. A local build and milestone notes are available.

## 18. Deliverables

Xcode project and Swift source; runnable local app; build/run instructions; completed acceptance checklist; and next-stage notes.

Public signing, notarization, distribution, and a polished installation DMG remain later release work.

The result is a working editor shell that can be opened, resized, renamed, and reset, ready for Test Mode, projector output, and the mapping engine.
